# Provisional report-attempt limits

The report Livewire action admits at most 3 attempts per browser session and 300 per client IP in aligned 600-second UTC epoch windows. Attempt 4 in the same session is blocked until the aligned window ends. Optional environment names (defaults work without editing `.env`): `REPORT_LIMIT_SESSION_ATTEMPTS`, `REPORT_LIMIT_IP_ATTEMPTS`, `REPORT_LIMIT_WINDOW_SECONDS`. Values must be positive integers. These are provisional policy, not measured production traffic requirements.

Every submission-action call counts before form validation or Turnstile, including missing/invalid CAPTCHA and invalid form data. Field updates, school search and temporary uploads do not count. Blocked requests increment neither counter and do not extend the window. The message gives minutes/seconds remaining until the fixed boundary. Draft fields/uploads remain intact; verification resets for a fresh retry. Fixed windows allow boundary bursts; a session can be replaced by clearing cookies, so the higher IP ceiling is a separate safety net. This is not durable report idempotency.

Uses the existing `database` cache store regardless of the default cache driver. A short supported cache lock wraps only admission. Both counter rows are initialized/read/locked through DatabaseStore APIs in deterministic order within one database transaction, then both increment or everything rolls back. Row locks protect admission if the outer lock lease expires. HTTP verification, attachments, reports and email occur after release. Lock/storage/configuration failures reject safely without processing a report, using a temporary-unavailability message. No limiter data or raw session/IP identifiers are logged; identity keys use HMAC with the application key.

The admission lock has a five-second lease and waits up to three seconds per acquisition. Known transient database deadlocks/lock-wait errors get at most three acquisition attempts with 50ms backoff; counter transactions also use bounded Laravel deadlock retries. A committed admission is never retried if releasing the outer lock fails. These infrastructure waits are separate from the policy's retry countdown. Logs contain only exception class and SQLSTATE/driver codes, never SQL, exception messages, identities, tokens or form contents. Logging failure does not change admission's outcome.

Hosting prerequisites: shared transactional cache database, `cache` and `cache_locks` tables with unique key indexes, consistent cache prefix/application key and synchronized clocks across workers. Repository migration `0001_01_01_000001_create_cache_table.php` defines the tables. No migration is run on an existing database by this change. Keep cache connection/lock settings pointing at shared storage. Client IP uses Laravel `request()->ip()`; do not trust arbitrary forwarded headers. Confirm the real proxy chain before enabling trusted proxies, and confirm the client IP observed behind Cloudflare/reverse proxies. Without that, all clients may share the proxy IP ceiling.

Testing: `php vendor/bin/phpunit -c phpunit.turnstile.xml` uses isolated SQLite, mocked Siteverify and non-sending mail. The separate `tests/rate-concurrency.php` harness requires explicit opt-in, connects only to a loopback MySQL/MariaDB server, creates a randomly named disposable database, uses real database cache/locks, and drops only that guarded database. It never reads or writes tables in the existing application database. Credentials are supplied through process environment, not command arguments or source. No app server is needed.

Harness environment names: `REPORT_RATE_TEST_ENABLE=1`, `REPORT_RATE_TEST_HOST=127.0.0.1`, `REPORT_RATE_TEST_PORT`, `REPORT_RATE_TEST_USER`, `REPORT_RATE_TEST_PASSWORD`. The local account needs permission to create/drop disposable schemas. Run `php tests/rate-concurrency.php` after supplying these privately. The harness uses the actual 3/session and 300/IP policy, including 299 preloaded IP attempts before concurrent admission, separate shared-IP sessions, blocked Livewire submissions, preserved temporary uploads, verification outside locks, aligned-boundary retry and infrastructure failures.

Database cache expiration does not guarantee physical removal of old bucket rows that are never read again. Arrange routine pruning of expired `report-attempts:` cache entries as part of cache-table maintenance; do not flush unrelated application cache data. This change does not add a scheduler or modify existing database maintenance.
